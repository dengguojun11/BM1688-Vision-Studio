# RUN-0239 边端人工探测结果防旧后台覆盖

日期：2026-09-20  
层级：本地 L1（生产未变更）  
责任角色：R03 架构、R04 后端、R07 BM1688 边端、R09 测试、R10 运维  
工作包：WP2、WP3、WP5、OPS

## 1. 问题与影响

边端设备创建后会自动启动一次环境检查。用户也可以在设备管理页面手工点击“探测”。两条路径可能同时执行 SSH 探测，并且都写入设备的 `probe_*` 状态。

旧实现中，后台检查先读取设备状态，然后在 SSH 检查完成后直接写回结果。如果用户在这段时间完成了手工探测，后台线程仍可能把较旧的连接失败结果覆盖掉较新的人工结果。例如人工结果已经是 `auth_failed`，页面最后却显示为后台线程写入的 `connect_failed`。这会误导设备分配和 BM1688 验证判断，也会让运维无法区分最新一次人工操作和历史后台检查。

## 2. 本轮规则

1. 后台环境检查开始时保存 `probe_status`、`probe_stage`、`probe_code`、`probe_checked_at` 四个字段的快照。
2. SSH 检查结束后重新读取设备记录；快照未变化时，后台结果才可以写入 `probe_*`。
3. 快照发生变化时，说明人工探测或其他更新已经产生较新结果，后台结果只记录自己的环境检查状态，不覆盖人工探测结果。
4. 环境安装、环境就绪和环境异常仍写入独立的 `environment_*` 字段，不能因为保护人工探测而丢失环境检查审计信息。
5. 该规则是并发写入防护，不改变 BM1688 只加载/推理、服务器负责编译的边端职责，也不引入设备发布、OTA 或模型回滚。

## 3. 代码与测试

| 文件 | 变更 |
|---|---|
| `labelu/internal/application/service/edge_device_registry.py` | 新增 `_probe_snapshot`；后台环境检查写回前重新读取快照；快照变化时跳过旧后台 `probe_*` 写入，仅继续持久化环境检查结果 |
| `labelu/tests/internal/application/service/test_edge_device_registry_environment.py` | 新增后台探测不能覆盖较新人工 `auth_failed` 结果的回归测试 |

## 4. 验收证据

修复前全量回归出现 1 个顺序相关失败：

```text
test_edge_devices_probe_updates_device_status
期望：auth_failed
实际：connect_failed
```

修复后专项验证：

```text
边端环境/路由专项：4 passed
BM1688 设备测试文件：38 passed, 1 skipped
py_compile：通过
git diff --check（目标文件）：通过
```

修复后后端全集：

```text
2636 passed, 56 skipped, 410 warnings
```

全集结果说明该修复在完整测试顺序下不再出现旧后台结果覆盖人工结果的问题；警告为现有测试环境警告，不改变通过结论。

## 5. 页面与接口表现

- 设备管理页面仍使用居中弹窗进行探测，不增加抽屉或新的设备菜单。
- 用户手工探测返回的认证失败、连接失败和成功状态保持为最新 `probe_*` 结果。
- 环境检查状态单独展示为环境就绪、环境异常或待处理，便于运维判断是否可以进入编译/验证队列。
- 设备状态变化不会修改模型发布目录、AICM 编号、本平台下载开关或第三方 S3 回流关系。
