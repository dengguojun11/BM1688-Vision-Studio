## 3. 并发档位证据边界

- 训练 Worker：本地 SQLite 已有 20 进程单赢家测试，没有 50 进程测试。
- S3 回流 Worker：本地 SQLite 已覆盖 2、10、20，没有 50 进程测试。

- `scripts/rehearse_mysql_concurrency_matrix.py` 虽然会编排 `2/10/20/50`，但它操作的是临时合成 InnoDB 表，不能替代训练、BM1688、边端、S3 四张业务表证据。

## 4. 发现的问题与风险

### 4.1 重复提交不是租约问题

任务创建和手工训练创建接口没有请求幂等键。即使后续 Worker 有队列租约，同一个用户快速重复提交仍可能先创建两个任务或两个训练作业，再分别排队执行。要修复必须先确定：

1. 幂等键由前端生成并通过 `Idempotency-Key` 传递，还是由服务按任务、数据清单、训练配方和用户生成业务键。
2. 相同请求重试返回原对象，还是返回冲突；有意创建同配置第二个训练作业是否允许。
3. 业务键需要新增哪张表/哪组唯一索引，以及历史数据重复如何处理。

这涉及 API 契约、数据库唯一约束和用户交互，不能在本轮并发审计中直接猜测或修改。

### 4.2 真实数据库性能尚未证明

当前所有业务链路并发证据都是 SQLite 或函数级测试。MySQL 迁移闸门要求的备份恢复、锁等待和 `2/10/20/50` 只能在隔离沙箱执行；不得把本机业务库或生产库作为替代。

### 4.3 边端资源维度缺失实测

队列租约只保护数据库任务行；BM1688 板卡数量、GPU 槽位、TPU-MLIR 编译进程、S3 带宽和设备重启耗时需要独立容量基线。没有这些数据，不能把“50 并发通过”解释为平台可承诺的 50 路业务吞吐。

## 5. 本轮处理决定

本轮**没有安全的最小业务代码修复**：

- 为任务/手工训练增加幂等，需要新增请求契约和唯一索引，缺少产品决策与 MySQL 迁移证据。
- 将本地 S3/训练测试直接扩大到 50 进程，会增加 Windows 进程启动和 SQLite 文件锁等待，不能替代 MySQL 证据，且可能造成不稳定测试。
- 将通用矩阵脚本改为直接操作四张业务表，需要真实沙箱、脱敏快照和各表状态机映射，不能在当前环境安全完成。

因此本轮只保留审计文档和已有专项验证结果，不修改业务代码、测试契约或数据库结构。
