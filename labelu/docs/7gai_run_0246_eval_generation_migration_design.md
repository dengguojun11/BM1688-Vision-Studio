- 责任角色：R03 架构、R04 后端、R06 模型算法、R09 测试、R10 运维

- 涉及菜单/按钮：训练中心“查看日志/指标”；模型中心“查看模型版本”和“质量证据”
- 验收等级：L0；未生成正式迁移、未连接生产

## 1. 当前证据与边界

正式 Alembic 当前唯一 head 为 `z9f3a4b5c6d7`。迁移放行测试要求在新增正式迁移前具备同版本 MySQL 沙箱、重复升级、备份恢复、锁等待和 `2/10/20/50` 并发证据。当前这些证据尚未提供，因此本轮不生成正式迁移，不改变生产数据库结构。

RUN-0245 已使用现有状态字段完成数据库条件领取，但状态字段本身只能防止两个进程同时从空闲状态开始，不能区分“旧进程和新进程都处于 RUNNING”这一恢复场景。

## 2. 目标数据模型

### 2.1 训练作业上的当前代次

在 `yolo_train_job` 增加两个可空字符串字段：

- `ai_eval_full_operation_id VARCHAR(64)`：全量评估当前执行代次。
- `ai_eval_next_operation_id VARCHAR(64)`：下一轮评估当前执行代次。

领取评估时生成新的随机操作编号，并在一次条件更新中同时写入 `RUNNING` 和对应操作编号。接管或重试必须生成新编号，不能复用旧编号。

### 2.2 报告上的来源代次

在 `yolo_eval_report` 增加：

- `operation_id VARCHAR(64) NULL`：报告属于哪一次评估执行。

增加唯一索引：

```text
(yolo_train_job_id, report_kind, provider_key, operation_id)
```

历史报告的 `operation_id` 允许为空，保留历史数据；新评估报告必须有操作编号。这样同一次 Provider 重试不能重复落两条结果，但不同执行代次仍可保留历史。

## 3. 写入规则

1. 领取：按作业、评估类型、旧状态和旧操作编号做条件更新；影响行数不是 1 时失败关闭。
2. Provider 调用：请求上下文携带当前操作编号，但不把密钥写入日志或报告。
3. 报告写入：按作业、类型、Provider 和操作编号幂等写入；唯一冲突读取已存在结果，不重复调用后续副作用。
4. 完成/失败：只允许操作编号仍等于当前作业代次的进程把状态从 `RUNNING` 改为 `COMPLETED` 或 `FAILED`。
5. 恢复：发现 `RUNNING` 且无对应代次报告时，只能生成新代次接管；旧进程迟到写入会被唯一键和条件状态更新拒绝。
6. 手工评估与自动评估共用同一套领取和结果写入函数，不另建第二种状态机。

## 4. 迁移执行顺序

正式迁移候选必须按以下顺序准备：

1. 生产脱敏快照在同版本 MySQL 沙箱恢复。
2. 首次升级增加可空字段和唯一索引，历史报告不回填伪造代次。
3. 重复执行升级，确认幂等；确认旧版本报告可正常查询。
4. 使用 `2/10/20/50` 并发模拟两个评估调度器、Provider 超时、进程重启和旧代次迟到写入。
5. 采集锁等待、死锁、重复报告数、旧代次拒绝数和恢复耗时。
6. 备份恢复到独立目标，再执行查询和一条受控本地评估回放。
7. 通过正式迁移闸门后，才允许生成正式 head 并进入预生产。

## 5. 本轮不改代码的原因

当前测试库使用 `Base.metadata.create_all`，可以提前验证 ORM 字段，但这不能证明生产数据库已有字段。若现在直接把新字段接入生产路径，旧数据库会出现“列不存在”或部分写入，违反一期 Worker `fail-closed` 要求。因此本轮只冻结设计、索引语义和放行证据；代码保持 RUN-0245 的无迁移条件领取实现。

## 6. 菜单与角色影响

- 标注人员：只查看评估状态、指标和质量证据，不感知操作编号。
- 管理人员：在系统管理中查看异常评估、重试失败阶段和迁移/并发证据；不能手工改写执行代次。
- 训练中心和模型中心继续使用同一训练作业、模型版本和质量证据真源，不新增“评估任务”一级菜单。
- 所有确认、重试和异常详情继续使用居中弹窗，不增加项目/业务空间维度。
