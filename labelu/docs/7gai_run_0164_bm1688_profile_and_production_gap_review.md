# RUN-0164 BM1688 配置档案与生产差距产品审计

> 审计日期：2026-09-20  
> 责任角色：R01 产品、R03 架构、R06 模型算法、R07 BM1688 边端、R09 测试、R10 运维  
> 工作包：WP0/WP3/WP5  
> 性质：只读产品与生产差距审计；本轮不修改业务代码、数据库或生产配置，不提交、不推送、不部署。

## 1. 结论

方案的主链路是正确的：

```text
任务/标注 -> 预标注 -> 人工确认 -> 训练 PT -> ONNX -> BM1688 BModel
-> 真实 BM1688 验证 -> AICM 发布/目录
```

“服务器编译、BM1688 只负责加载和推理”也符合当前生产技术边界。作为目标蓝图可评为 **8/10**；作为今天可以直接放量的生产方案只能评为 **4-5/10**。主要原因不是菜单不够，而是生产还缺少统一的编译配置档案、可验证模型清单、真实板端/Worker 证据和外部 ID 对账。

本轮最重要的判断：

1. PT、ONNX、BModel、发布包应属于同一个不可变模型版本，但必须由机器可读且可签名的 `ModelManifest` 连接；页面文字说明不能代替运行时校验。
2. “掉点阈值”只能作为同一封存验收集上的回归门禁，不能当成所有模型、所有类别和所有前后处理的通用算法真理。
3. 三种精度可以全部编译和留存，但不应默认每次都对三种精度执行同等强度的完整性能/长稳验收；发布精度才执行完整硬门禁，其余精度至少完成完整性、加载和同批精度烟测。
4. 本地测试通过不等于生产可用。真实 TPU-MLIR、BM1688、systemd、生产 MySQL、S3/AICM 对账和线上路由切换仍是放行条件。

## 3. 2026-09-20 生产只读事实

本轮仅访问生产 HTTP 只读入口 `http://113.141.72.175:10000`，没有写任务、模型、S3 或数据库：

| 探针 | 结果 | 产品含义 |
|---|---|---|
| `/openapi.json` | HTTP 200，`application/json`，约 742 KB | 线上确实存在可读 OpenAPI，但需按目标版本继续核对 |
| `/healthz`、`/readyz`、`/version` | HTTP 200，但 `text/html`，返回 SPA 页面 | 不能把 200 当健康/版本验收；Nginx 或应用路由仍需修复 |
| YOLO/BM1688 路由 | 生产 OpenAPI 可见现有训练、导出、验证、发布和板端接口 | 只能证明入口存在，不能证明真实 Worker/工具链/设备已通过 |
| S3/AICM 路由 | `/api/v1/strategy-integration-s3-config`、`/api/v1/published-models` 等路由存在 | 需要带生产账号做对象包、AICM ID、目录和回执三方对账 |
| 退休设备作业路由 | OpenAPI 仍暴露 `/api/v1/edge-device-jobs*` | 与一期“只做真机验证、不做设备发布控制面”的目标冲突，必须下线或只读隔离 |
| 目标聚合路由 | 生产 OpenAPI 仍未出现规范的算法目录、模型版本、工作台汇总等目标入口 | 方案菜单不能先于后端真源上线；应先补路由和数据迁移 |

生产已有数量只能引用冻结窗口快照。方案中的 2026-09-16/17 训练、导出、验证和发布数量不能直接当成当前数量；迁移必须重新盘点并以训练权重摘要、导出关联、发布关联和 AICM 目录去重。

## 4. P0 下一轮必须实现

### P0-1 统一 BM1688 Profile

建立唯一的、版本化的 `BM1688Profile`，编译节点、质量评估、Board Agent/SSH 验证和发布门禁全部读取同一份快照。至少包含：

- 模型族和真实权重摘要，不用默认 `yolov11n` 猜测文件前缀；
- ONNX opset、静态 batch、输入尺寸、NCHW/RGB、归一化、letterbox 和坐标还原；
- 输出节点/shape/顺序，禁止把某一个 YOLO 版本的输出节点写死给所有权重；
- 类别名称和顺序、后处理版本、置信度/IoU/NMS 和最大检测数；
- BM1688 目标、TPU-MLIR/Docker image digest、运行包/固件/BMRuntime/BMCV ABI；
- INT8 校准集摘要、qtable 摘要、三种 BModel 文件摘要。

当前方案正文固定写“YOLO11”和规则版本 `bm1688-yolo11-detection-v1`，而仓库配置和生产运行目录大量沿用 `sophon-demo/YOLOv8_plus_det` 命名，并存在 opset 12/17 双路径。这不是页面文案问题，而是会导致错误的输出节点、qtable、文件前缀或 BModel 被误判为完成。必须先选择并验证真实生产 Profile，再开放自动编译。

### P0-2 ModelManifest 与签名

每次编译生成不可变 `manifest.json`，记录模型版本、数据快照、Profile、工具链、文件列表、SHA256、运行包 ABI、规则版本和 AICM 关联。SHA256 只能发现文件损坏，不能防止有权限的错误替换；生产发布包和板端加载前还必须校验受管签名（例如 Ed25519/HMAC）及防重放字段。缺清单、摘要或签名时，状态只能是“制品不完整/不可验证”，不得进入发布或真机成功。

### P0-3 三精度门禁分层

统一规则如下：

1. FP32/FP16/INT8 都可以作为同一模型版本的编译制品，不能拆成三个业务模型。
2. 三种制品都做文件完整性、加载、有效推理和同批精度烟测。
3. 实际发布精度才做完整性能、错误率、P95、短稳和必要的资源指标；非发布精度不自动获得发布资格。
4. `mAP50` 掉点只用于转换回归定位；最终放行还要看关键类别召回、小目标/场景分层、误检漏检、有效推理数、前后处理一致性和运行时错误。
5. 阈值必须保存规则版本和生效快照。0.005/0.010/0.020 只能作为首轮工程起点，待生产代表模型重复验证后再确认，不能把它们当成永久标准。

### P0-4 修复生产探针和 OpenAPI 版本门禁

部署目标版本后必须验证状态码、Content-Type、JSON 首字符、版本号和时间戳。`/healthz`、`/readyz`、`/version` 不能被 SPA 回退吞掉；退休的 `edge-device-jobs`、项目/设备发布/OTA/回滚写入口不能继续出现在一期 OpenAPI。探针修复前，不得以 HTTP 200 或进程存活宣称生产可用。

### P0-5 完成 S3/AICM 三方对账

生产事实应固定为：第三方把图片和 `metadata.json` 写入约定 S3/MinIO，再通过策略任务通知 LabelU；`/strategy-integration-s3-config` 只维护连接，不产生问题图片。下一轮必须用真实脱敏包验证：

- AICM 模型 ID 能唯一解析到平台目录、模型版本、发布包和标签契约；未知/冲突 ID 进入 `WAITING_FOR_MODEL`，不猜测匹配；
- metadata schema、对象存在性、图片摘要、外部任务 ID 和幂等键均有校验；
- 重复通知不会重复建任务、样本、预标注或训练轮次；
- 导入、预标注、质量分流和回执失败可重试，失败原因可见；
- 真实 AICM 发布编号、平台目录编号、S3 metadata 三方可导出对账。

### P0-6 完成执行器放量前置

上述 P0 不能只在页面上实现。必须在同版本 MySQL/脱敏快照、systemd、真实编译节点和至少一台 BM1688 上完成单任务、重启、租约过期、旧 Worker 迟到写入、板端离线和恢复演练；在此之前保持 Worker/自动回流开关关闭或失败关闭。

## 6. 放行结论

本轮不改变方案的六个一级菜单、两类登录角色或第三方问题图片来源定义。建议按以下顺序继续：

```text
统一 Profile/Manifest/签名
  -> 修复生产探针和退休路由
  -> 真实 BM1688 + Worker 重启/租约演练
  -> S3/AICM/平台目录三方对账
  -> 生产代表模型阈值标定
  -> 只开放一条真实主链和一个真实回流包
```

在上述证据完成前，本方案只能标记为“目标蓝图 + 本地 L1/本机 MySQL 沙箱证据”，不能标记为“BM1688 生产闭环已验收”。本轮没有新增代码测试；生产探针结果属于只读证据，不替代真实设备、AICM、S3 或 systemd 验收。
