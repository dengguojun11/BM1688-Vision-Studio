# RUN-0244 角色开发交付文档机制审计与补充

- 日期：2026-09-20（Asia/Shanghai）
- 类型：只读文档审计与交付规则补充
- 责任角色：R01 产品、R03 架构、R08 前端/UI、R09 测试、R10 运维
- 工作包：WP0（产品与权限）、WP1（标注与数据契约）、WP2（训练与执行器）、WP3（模型中心与边端）、WP4（回流与外部平台）、WP5（测试与生产放行）
- 验收等级：L0（文档机制完成）；未修改代码、未提交、未推送、未部署、未连接生产写入

## 1. 审计结论

当前 `7gai_role_delivery_plan.md`、`7gai_role_execution_playbook.md` 和 `7gai_delivery_ledger.md` 已经覆盖以下机制：

1. 系统登录用户只有“标注人员、管理人员”；R01-R10 是研发交付责任，不是新增登录角色。
2. 每一轮使用 `RUN-编号`，并记录责任角色、工作包、代码/页面/API/数据库范围、测试证据、生产边界和 L0-L4 等级。
3. 本地 L1、预生产 L2/L3、生产 L4 分开判断；没有真实 S3、AICM、MySQL、TPU-MLIR、BM1688、systemd 或浏览器证据时不能写成生产完成。
4. 训练、编译、边端、回流 Worker 的租约/fencing、幂等和失败关闭属于验收内容；用户未明确“提交代码”前不提交、不推送、不部署。

因此，“每次产出都有对应文档方案”的总原则已经存在，不需要另建一套项目管理系统。

## 2. 发现的文档缺口

### 2.1 六个一级菜单没有一张完整按钮总表

现有章节分别描述了任务与标注、训练中心、模型中心、进化中心和平台设置，但工作台没有同样粒度的按钮验收表；模型中心、进化中心和平台设置的部分按钮仍以段落描述。后续实现容易出现“代码已做，但没有明确谁验收、什么证据算通过”。

### 2.2 菜单命名需要固定同义词

一期统一使用以下六个一级菜单名称：

| 菜单序号 | 页面名称 | 说明 |
|---|---|---|
| 1 | 工作台 | 展示当前账号可见任务、训练、模型和异常摘要，只做快捷入口，不创建新业务对象 |
| 2 | 任务与标注 | 创建任务、上传/导入图片、自动预标注、人工确认、冻结数据、创建训练 |
| 3 | 训练中心 | 创建训练作业、选择基础模型或历史 PT、查看日志指标、取消/重试 |
| 4 | 模型中心 | 模型版本、边端编译、真机验证、发布记录、下载目录 |
| 5 | 进化中心 | 第三方 S3 问题包自动接收、去重、聚合、复用/创建任务、异常处理和抽查；历史“数据回流”仅作为兼容叫法 |
| 6 | 系统管理 | 标签契约、预标注兼容关系、质量门禁、BM1688 Profile、设备、AICM、S3、下载开关和运行开关；历史“平台设置”仅作为兼容叫法 |

页面、路由、按钮、测试标题和运行文档必须使用上表名称。不得同时把“数据回流”和“进化中心”当成两个一级菜单，也不得把“平台设置”重复做成第七个菜单。

### 2.3 每轮文档还要补对象级证据

现有 RUN 模板已经要求测试命令和环境边界，但为了让交付可追溯，每轮还必须留下：请求编号、任务/数据集版本/训练作业/模型版本/导出记录/回流批次/设备任务等对象 ID；对应日志或截图路径；以及失败时的错误码和重试结果。没有对象 ID 的“通过”只能算静态 L1。

所有新增、编辑、危险确认、发布和下载控制均使用居中弹窗；按钮必须具备可用、处理中、成功、失败、空数据和无权限状态。不得用抽屉替代，也不得增加项目/业务空间选择。

## 4. 每轮产出文档的强制字段

每个工作包的代码或页面产出必须同时产生一个独立 `labelu/docs/7gai_run_<编号>_<主题>.md`，并在角色方案和交付台账各增加一条摘要。独立文档至少包含：

1. 本轮目标、涉及菜单和具体按钮；主责、协作、验收角色。
2. 业务前置条件、两类用户权限和状态转换；是否创建或复用任务、数据版本、训练作业、模型版本、回流批次或设备任务。
3. 改动文件、路由/API、数据库/迁移、配置、制品和外部系统范围。
4. 幂等键、租约/fencing、并发限制、资源上限、超时、失败关闭、重试和审计行为。
5. 测试命令、通过/失败/跳过数量、隔离库或环境、请求编号和对象 ID；原始日志、截图或报告路径。
6. 本地、预生产、生产分别写明“已验证/未验证/不适用”；不得以 HTTP 200、模拟器、单条记录或静态路由存在替代真实证据。
7. 风险、下一依赖、开关状态、提交/推送/部署状态和 L0-L4 结论。

同一轮涉及多个菜单时，独立文档必须分别列出每个菜单的按钮影响，不能只写“联合回归通过”。

## 5. 后续开发和验收规则

- 先写本轮范围和验收证据，再改代码；代码完成后先本地 L1，再按依赖推进 L2/L3/L4。
- R01 在每轮冻结按钮语义和权限；R02 冻结数据/标签契约；R03/R04 负责事务、幂等和 fencing；R05/R06/R07 负责外部平台、算法和真机证据；R08 负责页面状态和中文弹窗；R09 负责可重跑证据；R10 负责真实环境和放行。
- 任何 P0 证据缺失，相关训练、编译、边端和回流 Worker 保持 `fail-closed`；不把本地测试通过写成生产完成。
- 发布到外部平台后不提供回滚按钮；模型出现问题时，由有权限人员关闭本平台后续下载并发布替代版本，保留 AICM `model_set_id` 和审计记录。

## 6. 本轮追加的训练 Worker 交付

在文档审计后，本轮继续由 R04 后端、R06 模型算法、R09 测试完成车牌训练子链的最小并发修复：

- 车牌分类、OCR、姿态组件的进度文件、PT/ONNX 制品复制和导出前增加 owner/token 执行世代复核。
- 组件状态和制品清单在事务写入前再次复核执行租约；旧 Worker 失租后不能发布迟到的组件状态。
- 无执行上下文的历史路径只有在确认没有有效执行租约时可写；租约查询异常改为失败关闭。
- 车牌制品增加执行世代标记，恢复时必须与当前 owner/token 和 PT/ONNX 路径一致。
- YOLO 主训练的训练开始、每轮、每批次和结束回调增加执行世代检查；失租时在下一训练边界抛出失败关闭异常，阻止继续发布进度边界。

代码范围：`labelu/internal/application/service/plate_recognition_train.py`；回归范围：`labelu/tests/internal/application/service/test_plate_recognition_train.py`。

本地证据：车牌专项 `31 passed, 116 warnings`；训练 Worker、阶段世代、测试集栅栏、运行时、队列、稳定性和 YOLO 回调联合专项 `143 passed, 118 warnings`。`git diff --check`、目标文件 `py_compile` 通过。

本轮仍未连接生产 MySQL、真实 GPU、TPU-MLIR、BM1688、S3、AICM 或 systemd；未提交、未推送、未部署。训练完成后的异步评估写入仍需下一轮统一 owner/token 或独立结果代次校验，相关 Worker 保持 `fail-closed`。

## 7. 本轮结论

本审计补齐“菜单/按钮/角色/工作包/证据”的统一对照和菜单命名口径，并同步到 `7gai_role_execution_playbook.md` 的工作台、进化中心和系统管理按钮验收；追加的车牌训练并发修复达到本地 L1。下一轮所有实现必须引用本文件第 3、4 节，继续使用 `RUN-0245` 及以后编号；在真实 MySQL、GPU/TPU-MLIR、BM1688、S3、AICM、systemd 和浏览器证据完成前，整体方案不能宣布生产完成。
